# 2026-10-31

## 探测 192.168.1.1 —— 这是另一台型号：ZXHN F7610U-C（非 F7610M0）

用 `printf '...' | venv-python zt.py`（root/Zte521，直接 root shell）实测，结论：**F7610M0 的 java 钩子自启法在这台上不适用**。

### 设备档案
- 型号 **ZXHN F7610U-C**（联通定制 CU 版；Web 首页 JS 里 `modelName = "ZXHN F7610U-C"`，telnet banner `F7610U`）
- SoC **ZX279131**（与 F7610M0 同芯片；/etc 下有 `BOB_GN28L96_*_ZX279131_*.bin`，kmodule 里 `plat-zxylzb_9131.ko`）
- 双核 Cortex-A53（cpu part 0xd03），`mem=512M`
- 内核 `Linux 4.1.25 #4 SMP Sat Jan 27 18:00:04 CST 2024`，aarch64，gcc 5.3.1 / buildroot 2017.05
- BusyBox 1.17.2，**无 dd / head / nandwrite / flash_erase**；有 hexdump/sed/awk/sha1sum/cpio/tar/gzip/xz、mtd_debug、ubiformat、setcap、chroot

### 平台差异（关键）
F7610M0 是 **Java/OSGi 插件平台**（osgid 反复拉起 /usr/java/bin/java）。
F7610U-C 是 **中兴 CSP 平台**：`/bin/pc` → `cspd`（主控）、buservice、httpd、telnetd、upnas/ossagentproc/voip/gdbus-server/gpon_omci。
**没有 /usr/java、没有 /usr/plugin、没有 osgid** —— 所以"把 java 换成 shell 脚本"这个钩子根本不存在。

### 文件系统 / 分区（256MB SPI NAND）
- `rootfs on / type rootfs (rw,size=211256k)` → **rootfs 是内存 ramfs**（每次开机从 framework 分区解压），改 / 内文件立即生效但**重启即丢**
- mtd5 usercfg 2MB jffs2 → `/userconfig`（rw，剩 1.5MB）
- mtd7/8 kernel1/kernel2 各 48MB
- mtd9/10 framework1/2 各 16MB → **squashfs**（magic `hsqs`，xz 压缩，实际约 4.8MB），两槽内容相同
- mtd11 preplugin_data 24MB jffs2 → `/usr/tmp`（ro 挂载），内含 `preplugin.img`(3.7MB) → loop0 → `/usr/pre_plugin`（squashfs ro）
- mtd12 plugin_data 97MB UBI → `/opt/cu/apps`（**ubifs rw，85MB 空闲**）
- mtd3 tagparam 1MB → /tagparam，mtd4 wlan 1MB → /wlan

### 启动链
busybox init → `/bin/shellproxy ttyAMA0 115200 /etc/init.d/rcS` → rcS
→ `/etc/rcS.d/S02wlan S20tsmac S30network S43BSPDriver S99modules`（模块 insmod 全在这里）
→ `. /etc/init.d/dbus-rcS`
→ `pc&` → cspd → 各服务
`S99modules` 里有官方注释 `# add user-defined startup scripts here`，但它在 ramfs 内，重启失效。

### 持久化钩子调查（未找到现成可执行入口）
- rcS 第 236-259 行：`overlay lowerdir=/usr/pre_plugin/pre_CuInform_$host_name upperdir=/opt/cu/apps/CuInformUpper → /CuInform`，**upper 在 ubifs 可写持久**
- 但 `/CuInform/bin/plugins/CuInform/files/` 里是编译好的二进制（CuInform、CuInform-inner、init.bin、m01_sig.bin）＋ config，不是脚本；`conf/ops/CuInform/control` 只有 Package/Version/Oui/Dir 四行
- dbus-rcS 只做 `/opt/cu/apps/tt/ufwmg → /usr/sbin/ufwmg` 的 symlink（tt 目录是空的），不执行
- dbus-rcS 里大段被注释掉的 `/etc /usr /lib` overlay 到 /opt/cu/apps 的方案（厂商预留但未启用）

### conntrack 现状（原厂未调）
max=16000 / buckets=3584 / count=18 / tcp_timeout_established=86400
（与 F7610M0 一样是低配默认，确实需要调）

### 操作注意
- **telnet 不能并发**：同时开两个会话会互相踢掉（报 "没有到主机的路由"），必须串行，且两次之间 sleep 2
- zt.py 用 `venv-python`（`/home/wen/.workbuddy/binaries/python/envs/default/bin/python`，已装 pexpect）；系统 python 和 3.13.12 都没装
- 设备 busybox 无 head/tail(有)、无 dd；用 `awk "NR>=N"` 代替 sed 分段（sed 有，但 awk 更稳）

## F7610U-C 开机自启已完成部署并三次重启验证（04:40）

**方案**：`/CuInform/CuInformLoader` 换壳（overlayfs upper 在 ubifs 持久），
壳 → `setsid hook.sh` → `user.sh` → `exec CuInformLoader.real`。
触发时刻 uptime≈71–79 秒。原插件链不受影响。

**当前生效**：max=30000 / buckets=30208 / tcp_est=3600 / port_range=1024-65535

**部署件**：`/home/wen/WorkBuddy/f7610m0/f7610u/boot/{install.sh,hook.sh,user.sh,CuInformLoader,rollback.sh,README.md}`
设备侧集中放 `/opt/cu/apps/mystuff/`。

### 三个新踩的坑（本地 zt.py 都记一下）
1. **设备无 base64**：`echo 'b64'|base64 -d` 会静默生成 0 字节文件。改用主机
   `python3 -m http.server 8901` + 设备 `wget` 拉到 `/upgtempfile`。
2. **cspd 会回刷参数**：设好的值可能被后来的进程覆盖，
   user.sh 末尾加了一次性延时复查（sleep 90 → 检查补设 → 退出）。
3. **`hook.sh &` 会留 Z 僵尸**：壳最后 exec 成常驻的 CuInformLoader.real，永不等子进程。
   必须 `setsid hook.sh </dev/null >/dev/null 2>&1`。僵尸被移进 cgroup.procs，
   宿主 init 也 kill 不掉，只能靠不产生它。
