## 设备 C（跳板 100.64.64.107）CPU 单核占用高排查（只读，未改动）

结论：**CPU0 被收包软中断独占，CPU1 完全闲置**，不是某个进程跑飞。

证据：

| 项 | CPU0 | CPU1 |
|---|---|---|
| `NET_RX`（/proc/softirqs 累计） | 109,359,971 | 2,938 |
| `softnet_stat` processed | 0x165e3cab ≈ 3.75 亿包 | 2,953 |
| `softnet_stat` time_squeeze | 105,041 | 0 |
| 5 秒 /proc/stat 采样 | softirq 370/500 = **74%**，idle 27% | idle 97% |
| 硬中断 `pp`（37） | 73,082,800 | 0 |
| 硬中断 `pon`（16） | 35,351 | 0 |

- `eth3` 只有单队列 `rx-0/tx-0`，`rps_cpus` = 0（RPS 未启用）→ 软中断无处迁移。
- 业务量：ppp0 发 462 GB / 4.09 亿包、收 14.8 GB / 1.15 亿包，开机约 9.6 小时
  → 平均约 1.1 万 pps，全是 PCDN 上行。
- 附带压力：conntrack 24,914 / 30,000 = **83%**（dmesg 里 table full 丢包 0 次）。
- `load average 3.1~3.3` 是**假象**：D 状态进程（top 里 `ksuperlog` 为 DW）撑起来的，
  整体 idle 88%、usr 0%、sys 3.8%、sirq 7.6%。
- 用户态无异常：top 最高 `simulation` 8.1%（瞬时），cspd/osgid/upnpd 全 0%，
  java 进程 1 个，`/usr/plugin/*.log` 仍停留在 11-03 22:59（钩子只跑过一次，未反复执行）。

可能的缓解方向（**尚未动手**）：给 `br0`/`eth3` 开 RPS 把 rx 分到 CPU1、挪中断亲和。
**注意（已纠正一次错误说法）**：提 conntrack max 到 65535 **不能**减轻 CPU 开销 ——
查表是 O(1)，桶 30208、条目 24914 平均每桶 0.82 条，链很短；当前 83% 既没触发
`early_drop` 也没 `table full`（dmesg 0 次）。提 max 只会让内存翻倍（约每条约 300B）、
后台 GC 每次扫的条目更多，唯一价值是**留容量防满表丢包**，与 CPU 无关。

## RPS 残留（重要发现，未清理）

用户回忆「以前设过 RPS，之后跳板机跑 PCDN 变慢」，实测：

- **光猫侧 RPS 从未生效**：`sw`/`eth3`/`nbif1`/`br0`/`ppp0` 的 `rps_cpus` 和
  `rps_flow_cnt` 全是 0，`rps_sock_flow_entries=0`。RPS 是运行期参数，**重启即清零**，
  所以历史上就算开过也没了。→ **RPS 不可能让光猫硬件加速失效**。
- **跳板机 100.64.64.107 上却留着畸形配置**：`end0` 的 `rps_cpus = 0x06`（= CPU1+CPU2），
  `rps_flow_cnt = 0`，`net.core.rps_sock_flow_entries = 0`，而 `end0` 硬中断全在 **CPU5**
  （74,892,666 次，其余核 0）。nproc=6，uptime 13.4 小时。
- 找不到任何持久化来源（`/etc/udev`、`NM/dispatcher.d`、`cron*`、`rc.local`、
  `/usr/lib/systemd/system` 全无 rps 字样）→ **运行期手工 echo 的残留**，因为没重启才一直留着。
- 后果：硬中断在 CPU5 → RPS 经 IPI 把 skb 搬到 CPU1/CPU2 处理，跨核 + 无 flow table
  （flow_entries=0 时 flow steering 缓存失效），cache 全丢、IPI 拉高时延。
  PCDN 对时延抖动敏感，这条比光猫任何设置都更像是「变慢」的嫌疑人。

待办（用户未发话）：把 `end0` 的 `rps_cpus` 清 0 再测一次 PCDN 速度。

## 在光猫上开 RPS 实测（2026-11-04 20:30，设备 C）

**结论：`eth3` 上开 RPS 有效，`sw` 上开无效（CPU1 一个包都不接）。**

- `sw`：设 `rps_cpus=3` + `flow_cnt=4096` + `rps_sock_flow_entries=32768` 后，
  CPU1 的 `NET_RX` 和 softnet processed **完全没有增长** → 中兴的 sw 收包路径绕过 RPS。
- `eth3`：同样设置后立刻生效，CPU1 的 `NET_RX` 从 3,009 一路涨到 29,937。
- `nbif1`（WAN 侧）**尚未开**。

实测（**早期 20 秒采样混入了业务量波动，74%→34% 那组不准，已作废**）。严谨 A/B：
同一时段关/开各 60 秒，用 /proc/stat 差值算，结果如下：

| 指标 | RPS 关 | RPS 开 |
|---|---|---|
| eth3 包速率 | 5,345 pps | 6,937 pps |
| CPU0 占用 | 49.1% | **40.9%** |
| CPU1 占用 | 3.3% | **19.4%** |
| 两核合计 | 52.3% | **60.3%**（↑8 点） |
| 每包 CPU 成本 | 0.0973 ms | **0.0858 ms**（↓12%） |

**正确认知**：RPS **不省 CPU，只削峰**。总核时一定上升（跨核 IPI + cache），
换来单核峰值下降和每包成本下降。用户看"整体 CPU 使用率"会发现反而变高，属正常。

天花板原因：`sw` 的包量比 eth3 还大但**不支持 RPS**，那部分永远锁在 CPU0；
所以 CPU0 只能从 49% 压到 41%，想再降只能挪 `pp` 硬中断（风险高，未做）。

副作用检查：`nf_conntrack_count` 正常波动，`sw`/`eth3`/`br0` 的 drop/errs 全 0，无丢包。

### nbif1 也开 RPS（同样 3 / 4096）

CPU0 纹丝不动（43.6% → 43.5%），CPU1 从 19.4% 涨到 27.3%，两核合计 63%→70.8%。
→ nbif1 的包确实能分走，但 **CPU0 一点不降**。

### 激进实验：把 `pp` 中断迁到 CPU1

**关键坑**：`echo 2 > /proc/irq/37/smp_affinity_list` **被拒绝（RC=1，读回仍 0-1）**，
必须写十六进制那个文件：`echo 2 > /proc/irq/37/smp_affinity` → RC=0，LIST 变 1。
`affinity_hint=0`（驱动没设 hint）。原来掩码就是 3，只是实际全黏在 CPU0。

迁移后 30 秒实测：

| 指标 | pp 在 CPU0（原） | pp 迁到 CPU1 |
|---|---|---|
| CPU0 | 43.5% | **29.3%** |
| CPU1 | 27.3% | **43.8%** |
| 峰值 | 43.5% | **43.8%** |
| 两核合计 | 70.8% | 73.1% |

**只是把瓶颈换了个核，峰值没降、总账还升 2 点** → 已回退 `echo 3 > .../smp_affinity`。

### 最终结论（这个平台的天花板）

- 单队列 `eth3`/`nbif1` + 单一 `pp` 中断 → **NAPI poll 只能在中断所在核完成**，
  RPS 只能搬 poll **之后**的 skb，搬不走驱动收包本身。
- 2 核设备必然有一个核是瓶颈，换到哪个核都一样（43~44%）。
- 光猫上真正吃掉 CPU 的是 softirq（两核合计 70%+），不是用户态进程
  （cspd/osgid/voip/smbd 全 0%）→ **关服务省不出 CPU**。
- 要再降只能**减少进栈包数**，即让硬件加速覆盖 PCDN 流量（3.75 亿包全进栈说明没覆盖）。

当前保留状态：`eth3` 和 `nbif1` 的 RPS 都是 `3` + flow 4096，`pp` 亲和回到 3。
RPS 每包成本确实低 12%，留着无害；但**重启即失效**。

**注意**：RPS 是纯运行期参数，**重启即失效**。要长期生效必须写进
`/usr/plugin/boot.d/root.sh`（我们有钩子）：
```
echo 32768 > /proc/sys/net/core/rps_sock_flow_entries
echo 4096 > /sys/class/net/eth3/queues/rx-0/rps_flow_cnt
echo 3    > /sys/class/net/eth3/queues/rx-0/rps_cpus
```
回退：`echo 0 > .../rps_cpus`，或直接重启。

## 工具坑（tools/tnt.py，自写的最小 telnet 客户端）

1. 设备 busybox 连续灌命令会**丢新命令的首字符** → 逐条发送 + 60ms 间隔。
2. 前台 `top` 会**吃掉后续命令的首字母**（'t' 是 top 的按键）→ 必须 `top ... < /dev/null`。
3. 设备**无 tail/head/md5sum**，取行尾用 `sed -n 'a,bp'`，校验用 `wc -c`。
4. `pkill -f "L 127.0.0.1:PORT:"` 会匹配到自己那条 bash 命令行 → **自杀**，别用这种写法。

1. **`/etc/sysctl.conf` 带 immutable 属性**（`lsattr` 显示 `i`）。必须
   `chattr -i` → 改 → `chattr +i` 恢复，否则 `sed -i` 报 `Operation not permitted`。
2. **`sed -i` 的重命名在部分挂载上 EPERM** → 改用 `sed 管道 + tee` 覆盖。
3. **.206 的 sudo 需要密码**（不是免密），密码同 ssh 密码 `wen`。
   脚本已改成兼容两态：`sudo -n true` 探一次，不通就 `echo wen | sudo -S`。
