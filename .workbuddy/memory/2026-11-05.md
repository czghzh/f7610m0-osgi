## 技术更正：`2>/dev/null` 写在重定向右边是无效的

实测（bash）：
```bash
echo 2 > /nonexistent/f 2>/dev/null      # 仍然报错！RC=1
echo 2 2>/dev/null > /nonexistent/f      # 静默生效
{ echo 2 > /nonexistent/f; } 2>/dev/null # 静默生效
```
根因：shell **按从左到右顺序处理重定向**，`> /bad` 打开失败立刻 return，
后面的 `2>/dev/null` 根本没执行。

要屏蔽"重定向目标不存在"这类错误，必须把 `2>/dev/null` **写在 `>` 前面**，
或用 `{ }` 包一层；或者干脆先 `[ -d ... ]` 判断。
（注意区分：`ls /nonexistent 2>/dev/null` 是命令自身报错，那样写是有效的。）

## 硬件加速（FFE/HFF）实测：容量瓶颈，且**已经顶满**（23:50，105 光猫）

**入口**：`/proc/net/fastforward/` 是个**目录**（不是文件），下面 40 个节点。
`cat` 它会报 `Is a directory`。

**关键参数**：

| 节点 | 值 | 含义 |
|---|---|---|
| `hff_power` | 1 | 硬件快转开 |
| `ffe_power` | 1 | 快转引擎开 |
| `route_entry_max_num` | **32000** | **L3 快转表硬容量** |
| `local_ff_entry_max_num` | 32000 | 本地表容量 |
| `bridge_entry_max_num` | 32000 | 桥表容量 |
| `ffe_expire_time` | **4500** 秒 | 表项老化（75 分钟） |
| `local_packet_max` | 600 | 本地包阈值 |
| `hff_stats_time` | 300 | 统计周期 |

**`ffe_paras` 两次采样（间隔约 4 分钟）**：

| 项 | 第 1 次 | 第 2 次 | 变化 |
|---|---|---|---|
| **L3 entries** | **32001** | **32001** | **0（顶死在上限）** |
| Local entries | 1003 | 1197 | +194 |
| ffe v6 entry num | 17306 | 17355 | +49 |
| L3 V6 Hff entries | 3652 | 3667 | +15 |
| **Set hff fail** | 26312 | **26323** | **+11（持续装载失败）** |
| packets | 927,527,199 | 927,758,663 | +231,464 |
| bytes | 800,083,115,293 | 800,279,687,534 | +187 MB |

**结论（重要）**：

1. 硬件加速**没有"频率/占用率"概念**，它的"满"表现为 **表项数顶在 max 上不动 + Set hff fail 持续增长**，
   不是 CPU 那种百分比。
2. 这台 **L3 表 32001/32000 已经顶满**，每分钟还有 2~3 次新连接装不进去 → 回退 CPU 慢路径。
   这就是 CPU 那 25% 的来源。
3. **瓶颈是容量不是吞吐**：快转 packets 9.27 亿 / 800 GB，增量仅约 900 pps，离吞吐上限远得很。
4. **`nf_conntrack_max` 与硬件快转表完全无关**。硬件表固定 32000，放宽 conntrack 到 50000
   只会让更多连接留在软件路径 → **CPU 反而更高**，对硬件加速零帮助。这是关键认知。
5. `ffe_expire_time=4500`（75 分钟）意味着表满后，新连接要等老连接自然老化才有位置。

**中断侧**：`pp` IRQ 37 全在 CPU0，累计 2.68 亿次（PP 引擎把包送给 CPU）；
`IPI1 函数调用中断` CPU1 收到 **1158 万次**——这是 RPS 跨核推送的代价，每批 skb 一次 IPI。

## 实测：快转表上限与老化时间**都能改**（本地设备 A，宿主机直连）

**入口变了**：宿主机现在有 USB 网卡 `enx00e04c680a76` = **192.168.1.100/24**，
直连 `192.168.1.1`（0.45ms）。这台是 **F7610M0，内核 `#72 SMP Aug 23 2022`**，
即 memory 里记的「设备 B」那版固件。当前 **entries 全 0**（无业务、无 WAN），
`lsmod` 里 `switch` 174KB 模块负责 hff/ffe。

### 1）两个参数都可写 —— `ls -l` 显示 `-r--r--r--` 是骗人的

```
-r--r--r-- 1 root root 0 /proc/net/fastforward/route_entry_max_num
-r--r--r-- 1 root root 0 /proc/net/fastforward/ffe_expire_time
```

权限位 444，但 `echo X > 该文件` **RC=0、回读生效**。
（/proc 的权限位只是 inode 显示值，真正能不能写看 file_operations 有没有 .write。）

### 2）`ffe_expire_time` 已验证**真生效**（硬证据）

| 动作 | Local entries |
|---|---|
| 原值 4500 时 | 16（历次 telnet 会话残留累积） |
| 改成 **10** 秒后等 35 秒 | **2**（只剩当前会话） |

16 → 2，老化确实按新值执行。**这个参数不是摆设。**

### 3）`route_entry_max_num` 能写，但**真实容量未验证**

| 写入值 | 回读 | MemFree | Slab |
|---|---|---|---|
| 32000 | 32000 | 318256 kB | 54376 kB |
| 65536 | 65536 | 318256 kB | 54392 kB |
| 131072 | 131072 | 318256 kB | 54392 kB |

**内存一个字节都没变** → 写入不触发任何重新分配，底层表不是按这个值预分配的。

两种可能：
- (a) 它只是插入时的上限变量，底层链表动态增长 → 改大安全但只在有流量时才占内存
- (b) 底层哈希桶固定 32000，改大只是放开了检查 → 超过 32000 条会越界

**这台无 WAN、无 L3 流量，造不出 32001 条快转条目，无法区分。**
要验证只能在有真实流量的机器上做（105 那台正合适：表已满、Set hff fail 持续增长）。

**设备 A 现状（测试后已归位）**：`route_entry_max_num` = **32000**（原值），
`ffe_expire_time` = **600**（保留改小，10 分钟）。

### 可落地的结论

105 那台表满、`ffe_expire_time` 还是 4500（75 分钟）→ 把它改到 600 能让满表更快腾空，
缓解 `Set hff fail`。这是目前唯一有实证支撑的改善手段；改 `max` 还有风险。
