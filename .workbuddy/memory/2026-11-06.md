**起点**：105 光猫（跳板 `100.64.64.105` → `192.168.1.1`）L3 快转表 32000 满，

### 三次采样

| 时间 | L3 entries | Local | Hff | ffe v6 | Set hff fail | packets | CTCOUNT | CPU |
|---|---|---|---|---|---|---|---|---|
| 00:00:46（基线） | **31049** | 3175 | 8002 | 18014 | 26552 | 937,580,557 | 27888 | — |
| 00:01:07（改后 21s） | 24042 | 1965 | 7056 | 14205 | 26553 | 937,620,426 | — | — |
| 00:03:35（改后 2.5min） | **985** | 113 | 305 | 581 | 26558 | 937,708,780 | 16123 | **9.81%**（11.15/8.48） |

**L3 entries 掉了 97%（31049 → 985）。** 僵尸条目被 30 秒老化清光了。

### 但这个效果**不能全算老化的功劳**

pps 对比（按 packets 增量）：
- 改前 21 秒：+39,869 → **1898 pps**
- 改后 148 秒：+88,354 → **597 pps**

**业务本身降了 3 倍**（凌晨 0 点，PCDN 流量低谷）。conntrack 也从 27888 掉到 16123。
所以 CPU 从 26% 降到 9.81%，**主因是流量降了，不是老化改善**。要等业务回升才能判断真实收益。

### 容量为什么没改（32000 → 40192 暂缓）

读数显示 `L3 entries` 只剩 **985**，离 32000 差得远——现在扩容毫无意义。
且扩容有未验证风险（改大不分配内存，可能是假上限，超了会越界）。
**结论：等业务高峰再看 L3 entries 会不会重新顶到 32000，那时再决定扩不扩、扩多少。**

2. `Set hff fail` 增速会不会归零 —— 判断满表问题是否解决

## 【更正】conntrack hashsize 的调整规则：**不可预测，且无法精确命中**

先更正两版错误说法：
1. ❌「40192 是 256 的倍数，写进去不会被圆整」——错，回读 40448
2. ❌「严格大于输入值的下一个 256 倍数」——也错，用 8 个点验证不成立

**实测全部数据（设备 A，内核 4.1.25 / #72，`echo X > /sys/module/nf_conntrack/parameters/hashsize`）**：

| 写入 | 回读 | 回读/256 |
|---|---|---|
| 1000 | 1024 | 4 |
| 20000 | 20480 | 80 |
| 30000 | 30208 | 118 |
| 39000 | 39424 | 154 |
| 40000 | 40448 | 158 |
| 40191 | 40448 | 158 |
| 40192 | 40448 | 158 |
| 50000 | 50176 | 196 |

**结论**：
- 结果永远是 256 的倍数，但**不是任何一个简单公式能算出的**（差值 0、1、2 档都出现过，且与当前值无关）
- `40191` 和 `40192` 都落在 **40448**，所以「想得到 40192」这个目标**做不到**
- 已排除异步延迟：写后立即读与 8 秒后读一致
- 缩小也生效（50176→40191 变 40448；→1000 变 1024），不是只能单向

**因此脚本决定：就写 40192，接受回读 40448。** 差 256 个桶（0.6%）对性能无影响，
不值得为凑数折腾。脚本里已加注释记录这 8 个实测点。

**RPS 侧**：`rps_sock_flow_entries` / `rps_flow_cnt` 走 `roundup_pow_of_two`，
40192 → 65536。脚本里**直接写 65536**，让写入值 = 回读值。

## 01:21 hashsize 圆整规律（推翻旧结论）+ 脚本改 40960

**旧结论是错的**：之前记「内核粗粒度上调、无法精确命中 40192」，
实际规律很简单——**hashsize 被上取整到 512 的整数倍**。

实测（内核 4.1.25 / ZX279131，写 hashsize 后读 nf_conntrack_buckets）：

| 写入 | ÷512 | 读回 |
|---|---|---|
| 32768 | 64.0 | 32768 |
| 39936 | 78.0 | 39936 |
| 39937 | 78.002 | 40448 |
| 40192 | 78.5 | 40448 |
| 40448 | 79.0 | 40448 |
| 40960 | 80.0 | 40960 |
| 40961 | 80.002 | 41472 |
| 41984 | 82.0 | 41984 |
| 45056 | 88.0 | 45056 |

即：512 整数倍 -> 原样；否则上取整到下一个 512 倍数。
40192 命不中是它本身 78.5x512，不是"公式不可预测"。
之前 8 点实测（1000/20000/30000/39000/40000/40191/40192/50000）全是非 512 倍数，
所以全都看到"被改"，误判成无规律。

**另一个坑**：`/sys/module/nf_conntrack/parameters/hashsize` 是 **write-only**，
`cat` 报「权限不够」（不是没有读权限位，是节点无 .show）。
校验只能写完后读 `/proc/sys/net/netfilter/nf_conntrack_buckets`。

**改动**（本地已改，未推送）：
`deploy/root.sh` / `rootsh/root.sh` / `f7610m0-osgi/deploy/boot.d/root.sh`
三处同步，md5 `d15b14b3f6a2ab8e62f3c10e2db3b0b0`，2810 B。
- `nf_conntrack_max`: 40192 -> **40960**
- `hashsize`: 40192 -> **40960**（回读正好 40960，buckets 与 max 1:1）
- 注释换成上面的 512 对齐规律表 + write-only 提示
- 其余（port_range / tcp_est 3600 / RPS 65536 / eth0-3 cpus=2）未动

本地设备实跑验证：MAX=40960 BK=40960，MemFree 315952->315944 kB（-8 kB，桶数组 320 KB 常驻）。

**待办**：等下次有其他改动时一起推 6 台 F7610M0 并重启，不要单独为这个重推一轮。
